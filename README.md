# Interference-Case Assistant (prototype)

Ask plain-language questions about radio-interference cases and get answers
you can verify. **All data is synthetic** (generated by `generate_data.py`).
No real NCC or operator records are used.

> Built with AI-assisted coding. I reviewed, tested and can explain every part.

## The problem
Regulators hold case records in tables. Staff want quick answers ("which cause
takes longest to resolve?") without writing queries, but an LLM that guesses
numbers is unsafe for decisions.

## Approach: the LLM never does the arithmetic
1. **Parse** the question into a small JSON query spec (LLM, or a rule-based
   parser when no API key is set).
2. **Validate** the spec against a whitelist of columns and values, so a model
   cannot invent fields.
3. **Run** the spec with pandas. Every number comes from code, so it is checkable.
4. **Explain** the result in plain language (LLM or template).

Unanswerable questions are refused rather than guessed.

## Data (all synthetic)
- `cases.csv`: 300 cases, 23 fields: location (region, state, approximate
  coordinates), operator (placeholder names), frequency and band, assigned
  frequency and licence power limit (licensed sources only), RF measurements,
  suspected vs confirmed cause, source and monitoring equipment, days to close.
- `measurements.csv`: timestamped RF samples (5 per measured case).
- `equipment.csv`: monitoring equipment metadata and calibration dates.
- **RF fields (power, noise floor, SINR, occupied bandwidth) are only filled
  for ~60% of cases**, as in practice. Averages skip blanks, and the assistant
  says how many cases each SINR answer is based on.
- `suspected_interference_type` is what staff first thought; `cause` is the
  confirmed cause. They differ in about 15% of cases.

## Run it
```
pip install -r requirements.txt
python generate_data.py          # creates cases, measurements, equipment CSVs
python assistant.py "Which cause takes the longest to resolve?"
python eval.py                   # accuracy against independent ground truth
pytest                           # unit tests
```
Optional LLM mode: `export ANTHROPIC_API_KEY=...` (model via `ASSISTANT_MODEL`).

## Evaluation
`eval.py` asks 20 questions and compares each answer with a separately written
pandas calculation. Result with the rule-based parser: **20/20**.

The evaluation earlier caught two real bugs: averages were rounded before
ranking (near-ties came out in arbitrary order), and "slowest" was misread as
"lowest" by a substring match. Both are fixed and covered by tests.

## Limits (be honest about these)
- The 20 questions use vocabulary the rule parser knows, so 100% is optimistic.
  Paraphrased questions are the real test, especially in LLM mode.
- Only three metrics (count, mean days, mean SINR) and one grouping level.
- Licence-limit and bandwidth fields exist but are not queried yet.
- Synthetic data has invented patterns; real data would be messier (missing
  values, duplicates, inconsistent labels).
- Privacy: real deployments would need access control, audit logs and
  de-identification before any record reaches an external model.
- Bias/fairness: counts by region can reflect where monitoring happens, not
  where interference happens. Results need interpretation, not blind trust.

## Next steps

and a side-by-side comparison of rule-based and LLM parsing.
